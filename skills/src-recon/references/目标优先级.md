## 理念先摆明（别用错）

> **评分只决定「先打谁」，绝不代表放弃。** 低分目标照样在范围内，只是排后面。
> 目标多到打不过来时，它决定你的顺序；目标只有一个时，它没用。

这条很重要：没有它，"评分"就会变成"自己给自己缩范围"，把可能出洞的资产排除掉。

## 正向加权（越像"有数据、有后台、有接口"越优先）

| 类型 | 权 | 关键词/特征 |
|---|---|---|
| 管理后台 | +3 | 管理后台 / 后台管理 / 管理系统 / 管理中心 / 控制台 / console / manager |
| 数据交互型 | +3 | 支付 / 缴费 / 考试 / 成绩 / 充值 / 转账 / 订单 / 申报 / 报名 / 审批 |
| 微信生态 | +2 | 微信管理 / 企业微信 / 公众号 / 小程序管理 |
| API 网关 | +2 | 开放平台 / 应用管理 / api 网关；`Server: APISIX / Kong` |
| 前后端分离（有真接口） | +2 | vue / react / nuxt / angular / `/api/` / swagger |
| 云存储暴露 | +2 | `x-oss-` / `oss-cn-` / `.aliyuncs.com` / sts / minio / bucket |
| 非标端口 | +1 | 不在 80/443 |
| 行业属性（教育等） | +1 | 大学 / 学院 / 学校 / 职业技术 / 教育局 / 科学院 / 研究所 |

## 负向降权（先放后面，但不是不打）

| 类型 | 权 | 关键词/特征 |
|---|---|---|
| 统一认证网关 | −4 | 统一身份认证 / 统一认证 / CAS / SSO / authserver / 登录中心 |
| 纯前端静态站 | −4 | 官网 / 新闻网 / 门户 / 首页 / 宣传 / 概况 / 简介 |
| 敏感单位（合规风险） | −3 | 党员 / 党建 / 党委 / 纪检 / 组织部 / 统战 / 信访 |
| 数据展示大屏 | −2 | 数据平台 / 数据中心 / 大数据 / 统计平台 / 可视化大屏 |
| 公开通用服务 | −3 | grafana / kibana / redis / zabbix / prometheus / jenkins / phpmyadmin |
| 知名开源 CMS | −1 | wordpress / wp-content / discuz / dedecms / phpcms |

> 负向里有两类**不是"价值低"而是"别碰"**：涉党/纪检这类敏感单位，以及 grafana/redis 这类
> 一眼就是运维内部组件的（打进去容易出事、也容易是蜜罐）。

## 通杀：一个洞确认后，问一句「能不能一打一片」

判据（三条同时满足才值得批量）：

1. 目标用的是**通用产品/框架**（同一套代码、同一版本），不是你手搓的业务逻辑；
2. 缺陷在**代码层/设计层**（默认口令、已知 CVE、通用鉴权缺陷），不是某台机器的配置疏忽；
3. 有同款规模（同厂商资产、同指纹、同 CMS、同供应链）。

做法：先在同款站点里**实证 2~4 个**（能多验几个就多验），再决定是否扩面。
在 pi-lab 里这天然是黑板上的动作 —— **一条 verified Fact（某指纹存在某缺陷）→ 生成 N 条并行 Step
（同指纹兄弟站点逐个验证）**，也就是 Cairn 的「一个 fact 派生多个 intent」：

```bash
# 主会话：拿到通杀判据后，直接批量建 Step（一轮最多 3 条，见 prompts/fgs-reason.md）
fgs step-add <pid> "对 site2 用同一 PoC 验证同指纹缺陷，判定式：<expression>"
fgs step-add <pid> "对 site3 用同一 PoC 验证同指纹缺陷，判定式：<expression>"
```

注意：**每个站点单独取证**（各自的请求/响应），不要拿 A 站的证据去证明 B 站。

## 死目标要快速放弃

一个目标连续两轮没有任何新事实、也没有可继续的攻击面 → **落一条"死路论证" Fact**
（哪个入口试过、结果如何），然后换下一个目标。别在没价值的目标上烧轮次 ——
SRC 的产出分布是**重尾**的：绝大多数目标没洞，少数目标出大洞。

> 配套：`收洞判定.md`（打到了算什么）、`skills/src-recon/SKILL.md`（识别 → 查库 → 验证 → 复审）。
