# SRC 打法 · 品类册（6 本）

> **设计原则：品类优先，不是数量优先。**
> 外部那些「103 个 skill」的库很全，但**全 ≠ 好** —— 逐类浅铺的后果是：
> 每类都只有 payload 清单、**没有判据**，实战时仍不知道「到底算不算打穿」。
> 所以这里按 **SRC 出洞品类**收敛成 6 本，每本做深。

## 为什么是这 6 个品类

| 品类 | 选择理由 |
|---|---|
| **1 访问控制** | OWASP API Top-10 **首位**；微信官方《常见风险》也排第一类；`authzdiff` 有工具支撑 |
| **2 认证与会话** | **危害天然成立**（拿到会话即接管），判据比越权简单，SRC 报价通常最高 |
| **3 业务逻辑** | 扫描器**结构上看不见**，最不容易被 AI 批量刷掉；竞态有 `h2spacex` 支撑 |
| **4 信息泄露与密钥** | **命中率最高、最不需想象力** —— XBOW「更土的路」的落点；`wxapkg.py scan`/`gitleaks` 支撑 |
| **5 注入** | **实锤危害最容易拿到**（RCE/文件读），判据清晰；WAF 绕过并入（同一类问题：让 payload 到达） |
| **6 基础设施** | 走私是复杂栈上 ROI 最高的 bug；但**需要真实多跳架构**，所以单独成册、按需查 |

**没进 6 本册的品类**（AD / K8s / 容器逃逸 / 移动端 / 桌面 / web3）：
属**内网与终端**，外网 SRC 面里优先级低 —— 需要时用 `bash tools/kb_fetch.sh hackskills` 现取，
**不占常驻**（见 `tools/TOOLS.md` 的外部知识基线）。

## 我做的「优化」（相对外部源 skill）

外部源（`yaklang/hack-skills` 等）**强在覆盖面，弱在判据**。本册每本统一做了四件事：

| 优化 | 具体 | 为什么 |
|---|---|---|
| **① 补确定性判据** | 每类都给「到哪一步才算打穿」，而不是只给 payload | 源 skill 大量只列 payload；**没有 oracle 就只会报一堆 200** |
| **② 适配本机工具** | 源写「用 Burp」→ 换成 `curl` / `playwright` / `authzdiff.py` / `h2spacex` / `wxapkg.py` / `fgs` | 我的工具链与源假设不同；**能直接跑的命令才算学到** |
| **③ 统一证据字段** | 每本末节给 `fgs fact-add` 的具体字段（含 `proof_kind`） | 让结论**能过门禁**（`fgs gate`），不是写在报告里的一句话 |
| **④ 加停止条件** | 多处写「试到第 3 次无反应就换」（对应 `doctor` 的 `attempts≥3 → 枯竭`） | 打 arXiv:2602.17622 的 Type B 根因：**过度承诺低价值分支** |

## 统一结构（每本一样，便于速查）

```
何时用        → 什么信号该翻开这一本
探测          → 用本机工具的具体命令（可直接跑）
判据          → 确定性判定式（机器可判，不是"看起来像"）
实战步骤/矩阵  → 该试什么，按维度逐个试
坑            → 踩过的，含边界（别脱库/别越界/别硬删）
证据怎么留     → fgs 字段 + proof_kind
```
