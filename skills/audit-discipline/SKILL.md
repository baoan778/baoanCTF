# 审计纪律 —— 防误报自检

> 这不是「怎么审计」的教程，是**我踩过的 6 个坑**的固化清单。
> 触发：任何「发现缺陷 / 根因锁定 / 问题清单」类结论**交付之前**必读。

## 核心事实

2026-11-13 一轮审计里，我报了 9 个真缺陷，同时产生 **6 次误报**：
误报率 40%。每次误报都浪费一轮排查，且会让人对我后续结论打折。

**误报不是「不小心」，是两类可复现的思维/工具习惯。**

## 两条根因

### 根因 A：工具匹配范围失控（4/6 次）

把「看起来像」当成「就是」：

| 踩坑 | 现象 | 教训 |
|---|---|---|
| `Select-String` 输出截断 | 读到 0.2.3，实际是 0.2.4 | **关键值必须读全文，不用截断输出** |
| 正则扫全文 | 报 42 条断链，实际 0 条 | **匹配前先排除注释、代码块、正文字符串、外部 URL** |
| shell `$T` 未展开 | 报 17 个工具缺失，实际全在 | **脚本里的变量先 echo 验证再判定** |
| 注释/正文混淆 | 读到 `UI_REQUIRE_TOKEN=1`，实际是说明文字 | **判定取值必须看赋值行，不看提及行** |

**强制动作**：任何「数量型」结论（N 条断链 / N 个缺失 / N 处超限），
**必须至少手工抽验 3 条**，确认真实性后才报数。

### 根因 B：从单次观察跳到结论（2/6 次，但代价最高）

最贵的一次：我说「根因锁定为 import fgs」，做了轻量对照实验后**当场被证伪**。

**强制动作**：宣布根因前必须回答三问：
1. **如果这是巧合，会是什么样？** → 设计一个能证伪的实验
2. **对照组是什么？** → 同条件但去掉可疑因子，结果是否改变
3. **样本量够吗？** → 1 次失败不等于稳定复现，至少 5 次

## 结论分级（交付时必须标注）

| 级别 | 判据 | 措辞 |
|---|---|---|
| **已证实** | 有对照实验 / 可稳定复现 / 逐字读到原文 | 「已确认」 |
| **高可能** | 有直接证据但未做对照 | 「证据指向」 |
| **疑似** | 只有单次观察 | 「疑似，待验证」 |

**禁止**：用「根因锁定」「确认」描述第 2/3 级。

## 交付前 6 问（逐条打勾）

- [ ] 每个数字都手工抽验过至少 3 条？
- [ ] 每个根因都有对照实验，不是单次观察？
- [ ] 读关键值时用的是全文，不是截断输出？
- [ ] 正则/grep 的匹配范围排除了注释、示例、外部引用？
- [ ] 结论标注了「已证实 / 高可能 / 疑似」？
- [ ] 有没有**先写「如果这是误报会是什么样」**再确认？

## 已知高频误报场景（遇到直接套）

| 场景 | 常见误报原因 |
|---|---|
| 文档引用路径「不存在」 | 可能是外部 URL、第三方包路径、其他项目文档 |
| 工具「不在 PATH」 | 可能在 venv/、第三方 bin/、需要包装脚本 |
| 数字不一致 | 可能是历史快照、注释说明、不同口径 |
| 测试「偶发失败」 | 先查是否**测试自己崩了**（取 `[-1]` / `json.loads` 未判空），不是被测代码问题 |
| 「配置与实际不符」 | 先确认读到的是**宿主文件**还是**容器内旧快照** |

## 一句话

**宁可说「疑似，待验证」，也不要说「根因锁定」然后被推翻。**
前者只丢一点面子，后者丢全部可信度。
